U[4]: explain why a database index speeds up reads and when it doesn't help
A[4]: A database index speeds up reads by allowing the database to quickly locate rows without scanning the entire table. Instead of performing a full table scan (which checks every row), an index acts like a book's index — it lets the system jump directly to the relevant data using a sorted lookup. This is especially helpful for queries that filter or sort on specific columns.

However, an index doesn't help in these cases:
- **Simple queries without filtering**: If a query retrieves all rows (e.g., `SELECT * FROM users`), there's no need for an index since the database must read every row anyway.
- **Low selectivity**: If the indexed column has many unique values (e.g., a user ID), the index may not reduce scan time much because the database still has to check many rows.
- **Highly selective queries**: When the query filters on a column with few distinct values (e.g., `WHERE status = 'active'`), the index can be very effective.
- **Frequent writes**: Indexes slow down write operations (INSERT, UPDATE, DELETE) because the database must update the index structure each time data changes. So, if writes are frequent, the cost of maintaining the index may outweigh the benefit of faster reads.

In short: indexes are great for fast reads on specific conditions, but they’re not useful when the query doesn’t filter or when the write overhead exceeds the read gain.
